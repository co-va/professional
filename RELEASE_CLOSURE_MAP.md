# Карта закрытия продукта: от F-контейнера до действия

**Состояние:** рабочая карта для исполнения, все элементы стартуют с «Не принято». Ни один технический статус ниже не означает, что тариф разрешает доступ или что функция имеет `AdminToolReadiness=READY`.
**Источник структуры:** `co-va/core/BUSINESS_ARCHITECTURE.md` (F / E / режим / capability).
**Машинный реестр:** `RELEASE_CLOSURE_REGISTRY.json`. Одна и та же запись не должна отдельно существовать в нескольких не связанных таблицах.
**Защита:** `scripts/release/verify-closures.mjs`. Не CI, не серверная функция и не новая UI-библиотека.

## 1. Как читается карта

| Уровень | Что означает | Что именно нужно закрыть |
| --- | --- | --- |
| **Тарифный релиз** | Start, затем Start+, затем Pro — *техническая программа выпуска*, не право доступа | Все включённые в выпуск бизнес-сценарии; отдельная матрица коммерческих прав Core |
| **F — контейнер** | Главная рабочая карта, например Журнал | Навигация, все предусмотренные режимы и возможности, правильный UI и данные |
| **E — инструмент** | Самостоятельная работа внутри F, если действительно существует | Собственный рабочий процесс, история, управление; без придуманной второй E |
| **Режим** | Способ увидеть одни и те же объекты, а не E | Представление, переключение, фильтрация, одинаковое состояние данных |
| **UI-компонент** | Мини-карта, список, календарь, Z/Q/X, кнопка | Единственный владелец, точный эталон формы, читаемость, размеры, поведение, мобильность |
| **Capability / действие** | Создать, перенести, оплатить, вернуть, продать | Реальная операция с подтверждённым сохранением, ошибками, повтором и историей |
| **Домен/API** | Record, Time, Finance и другие владельцы данных | Корректная транзакция, безопасность, единые факты, отсутствие вторых источников |

**Уровни не подменяют друг друга:** Журнал — F; День, Месяц, Список — режимы; График — подрежим Месяца; создание записи и оплата — capabilities. Никакой новой E для режимов Журнала.

## 2. Пример заполненной структуры: Start → Журнал

```text
START — технический выпуск
└── ЖУРНАЛ [F]                                         НЕ ПРИНЯТО
    ├── ДЕНЬ [режим]                                  НЕ ПРИНЯТО
    │   ├── Шкала/слоты [общий UI + Time]             НЕ ПРИНЯТО
    │   ├── Запись [capability]                       НЕ ПРИНЯТО
    │   │   └── Мини-карта [общий UI]                 НЕ ПРИНЯТО
    │   ├── Событие [capability]                      НЕ ПРИНЯТО
    │   └── Заметка [capability]                      НЕ ПРИНЯТО
    ├── МЕСЯЦ [режим]                                 НЕ ПРИНЯТО
    │   └── ГРАФИК [подрежим, НЕ E]                   НЕ ПРИНЯТО
    ├── СПИСОК [режим]                                НЕ ПРИНЯТО
    └── ОПЛАТА ЗАПИСИ [capability + Finance]          НЕ ПРИНЯТО

Другие обязательные контуры технического выпуска Start:
Профиль / Сервис / Контакты / Продажа вне записи / Финансы.
Они НЕ автоматически объявляются включёнными в коммерческий тариф Start.
```

Общие компоненты `miniCard`, Calendar, List, Z/Q/X и общие домены Record/Time/Settlement показаны в реестре **отдельными ссылками**, а не размножаются в каждой карте. Если общий компонент изменился, затронутыми считаются все закрытые сценарии, которые от него зависят.

## 3. Статусы без ручных пользовательских «галочек»

- **Не принято (`open`):** код может уже существовать и даже иметь отдельные зелёные тесты, но полная приёмка не доказана.
- **В проверке (`verifying`):** исполнитель сопоставляет реальный UI, бизнес-операцию и сервер на тестовой среде.
- **Закрыто (`locked`):** реальные сценарии и внешний вид приняты, сохранены доказательства и точная версия Git. Изменения без отдельного решения владельца не допускаются.

**Родитель нельзя закрыть, если не закрыты все обязательные дочерние элементы и зависимости.** Это вычисляемое правило — вручную статус контейнера «Готово» ставить недостаточно.

**Критерии по каждому элементу:**
- **Архитектурная чистота:** один владелец данных и UI, нет второй реализации того же действия, бессмысленных fallback/bridge, недостижимого кода и лишних локальных CSS-переопределений. Удаление только после проверки зависимостей и сохранения данных, не массовой зачисткой.
- **Визуальный:** пользовательски утверждённый эталон, без произвольной стилистики, дублей и лишних заголовков.
- **Интерактивный:** все предусмотренные действия реально работают; скролл/клавиатура/жесты не сдвигают Z/Q/X.
- **Данные:** тот же факт виден во всех режимах и после повторного входа, нет ошибок и ложных подтверждений; пробный платёж не дублируется.
- **Регрессионный:** сохраняется адресный проверочный сценарий с ожидаемыми результатами. Это **не** новый CI.

**Эталон нельзя определять наугад только потому, что в CSS уже есть число или размер.** Если карточка в User и Professional различается, сначала выясняется, какой вид согласован, и только затем делается точечная замена.

## 4. Что происходит после закрытия

1. Исполнитель фиксирует в реестре `locked`, основание пользовательской приёмки, дату, Git SHA и доказательства: снимки результата, выполненный сценарий, проверенную версию Core/API. Для UI необходимо подтверждение внешнего вида на устройстве.
2. При следующей работе исполнитель запускает короткую сверку: `node scripts/release/verify-closures.mjs`. Она проверяет дерево статусов и сравнивает изменённые файлы с сохранённым SHA закрытого элемента. Для Core и User нужен также отдельный осмотр их изменений и согласованных API — этот скрипт не имеет доступа к их локальным деревьям.
3. Если изменён файл или зависимый общий UI, используемый закрытым элементом, работа **останавливается до определения влияния**. Без отдельного согласования владельца менять этот контракт нельзя. После разрешённого изменения повторно выполняется только затронутый сценарий и заново фиксируется его эталон.
4. Проверки нельзя «чинить» переписыванием их ожидаемого результата. Правка теста, эталона, разрешённых зависимостей или замороженного SHA — **отдельное изменение контракта**, а не часть обычной разработки.
5. Перед релизом Start выполняется общий прогон Start; перед Start+ — Start и Start+; перед Pro — все три уровня. Не на каждый коммит. Никаких новых GitHub Actions.

## 5. Граница технической защиты

Скрипт — **обнаружение вмешательства**, не физический запрет записи в Git. Сейчас нет подтверждённого доступа к настройкам защиты веток GitHub (API вернул `403`), поэтому нельзя заявлять, что GitHub уже не пропустит изменение. Для **необходимого технического запрета** нужна настройка GitHub ruleset/защиты `main` с разрешением владельца на изменение замороженных контрактов; это отдельный доступ и отдельная настройка, она не требует нового CI, но может потребовать человеческого согласования таких PR.

До появления серверной защиты любой исполнитель обязан соблюдать эту карту; реальные ограничения должны подтверждаться на GitHub, а не обещанием другого чата. Изолированные тесты и запись в документе не гарантируют, что баг больше никогда не возникнет.

## Условие чистоты перед первым переносом Professional в main

**Ни Start, ни Start+ не считаются готовыми только потому, что интерфейс прошёл сценарии.** Перед принятием каждого элемента проверяется, что он использует каноническую реализацию; подтверждённые дубли и обходы удаляются **в этом же небольшом этапе**, а не переносятся в следующую версию. Это обязательное поле `architecture` в `RELEASE_CLOSURE_REGISTRY.json`.

Для **Журнала** последовательность: День (Time/Record/событие/заметка) → Месяц → График → Список → запись/miniCard/Z/Q → оплата/Finance → сквозная проверка. По каждому пункту сначала карта владельцев, затем точечная очистка и исправление, затем проверка поведения и визуального эталона. Нельзя закрыть контейнер Журнал, пока хотя бы один из них остаётся «Не принято».

**Граница:** не требуется «идеальный код всего репозитория» и не удаляются исторические данные/серверные контракты как «дубли». Нужна доказанная чистота **всех выпускаемых контуров и общих зависимостей**, сохранность старых фактов и отсутствие конфликтующих реализаций.

**Первый перенос в `main` запрещён**, пока не пройдены одновременно: функциональная, визуальная, архитектурная и API-проверки для фактически входящих в выпуск Start/Start+; просмотр итогового diff; отдельное разрешение владельца. Защитить пустующий `main` можно раньше: защита не означает публикацию.

## 6. Production: `main` под защитой, `staging` для будущего

**Защиту ветки `main` устанавливаем сейчас**, до утверждения коммерческого выпуска. На 13.11.2026 API GitHub подтвердил `professional/main.protected=false`, `professional/staging.protected=false`, а список rulesets пуст. Создание защиты через доступное подключение GitHub не разрешено (чтение branch-protection возвращает 403); не считать её включённой, пока GitHub не подтвердит `protected=true`.

Для `main`: обязательный PR, запрет force-push и удаления, запрет обхода администраторами; **никаких новых required CI/status checks**. Дополнительное требование стороннего одобрения не вводить без доступного второго утверждающего. Право владельца выпустить проверенную версию остаётся отдельным необходимым действием — автоматическая зелёная проверка не означает разрешение на релиз.

**Первый перенос в `main`:** после приёмки согласованного состава первого коммерческого выпуска. Если он включает Start + Start+, закрыть оба. Если отдельно согласован ранний Start-релиз — не ждать Start+ ради одной только смены ветки. В обоих случаях перед переносом проверить diff, не выпускать незавершённые Pro-функции и не опираться на один только зелёный `staging`.

**Amvera:** production Professional только с `main` **после** разрешённого переноса и проверки совместимости с реально развёрнутым Core API. На `staging` продолжить будущую разработку; отдельно сохранить доступ к тестовому предпросмотру, не публикуя его как production. Каждый релиз сохраняет Git SHA, проверку реального приложения и способ отката.

Полная последовательность в [`RELEASE_GATES_START_TO_PRO.md`](./RELEASE_GATES_START_TO_PRO.md) → «Выпуск, ветки и Amvera».

## 7. Что исполняем первым

**Журнал → День.** В текущей кодовой базе его владелец — `journal/день.js`, шкала — `ui/time/journal-day.js`, Record — `core/records/view.js`; интерфейсные зависимости отмечены в JSON. Проверяем связку формы, жестов, действий и данных; замечания исправляем по одному подтверждённому несоответствию. После адресной проверки закрываем только то, что действительно доказано. Пока `День` не принят, весь `Журнал` и технический Start остаются открыты.

**Стадия исполнения на дату создания:** реестр и ручная защита подготовлены, **ни одного закрытого элемента не объявлено**. Код Журнала и другие приложения этим документом не меняются.

## 8. Практический протокол поэтапной приёмки Журнала — 15.11.2026

**Назначение:** исполнение уже существующих элементов `RELEASE_CLOSURE_REGISTRY.json`, а не новый реестр, новый UI-контракт или отдельный журнал задач. Порядок ниже конкретизирует пункт 7. Каждый шаг включает проверку архитектуры, исправление *подтверждённого* отклонения, адресный тест и приёмку в реальном `professional/staging`. Режимы День / Месяц / Список и подрежим График не становятся E.

### Перед началом каждого шага

1. Считать фактический HEAD `co-va/professional/staging`, проверить активную сборку Amvera и фактическую версию Core API; не считать отправленный коммит автоматически развёрнутым. Сверить `PROJECT_STATE.md`, этот документ, `RELEASE_CLOSURE_REGISTRY.json`, `UI_ALPHABET.md` в Core и уже принятые сценарии.
2. Назвать **существующий ID реестра**, реального владельца UI и данных, зависимости и вызывающие поверхности. Проверить, нет ли двух обработчиков, двух представлений одних данных, повторных вычислений суммы, shadow-store, альтернативного модала, несовместимого локального CSS, неиспользуемых путей и устаревшего fallback. Ничего не удалять по совпадению названий: проверить достижимость и зависимости.
3. Подготовить контрольный сценарий: исходные данные → действия → ожидаемые факты → повторный вход → место, где факт должен быть виден. Исправление — **вместо** конфликтующей реализации, без создания параллельного UI и расчётчика.
4. Проверить на исходниках, в доступном браузерном runtime, через реальный сервер и на iPhone. Если какой-либо слой недоступен, отметить именно его «не проверено», не выдавая smoke за полную приёмку.
5. В *существующем* реестре заполнить пять полей `acceptance`: `architecture`, `visual`, `interaction`, `data`, `regression`. `locked` допустим только после их подтверждения владельцем, доказательств, версии приложения/API и Git SHA. Проверку `node scripts/release/verify-closures.mjs` выполнить до и после изменения закрытых областей.

### Обнаруженные незакрытые пункты при составлении маршрута

- `journal/день.js`, `ui/time/journal-day.js`: ранее исправлялся hit-test/нажатие; в реестре остаются `verifying`. Реальное нажатие и открытие на iPhone/Amvera ещё не подтверждены в карте приёмки.

- `journal/journal.js::openJournalZReport`: отчёты Дня и Месяца сейчас агрегируют сумму по `recordAmountDue`, платежи и Tips; **нет построчной расшифровки первоначальных стоимостей и скидок**. Полнота этих финансовых отчётов пока не принята.
- `journal.graph`, `journal.month`, `journal.list`, `journal.event`, `journal.note`, `journal.payment`: статус `open`, визуальная и сквозная приёмка не доказаны. Исполнением документа статус не менять.

### Норма для любого дефекта и для последующих изменений

- Установить воспроизводимый сценарий, корневую причину и владельца исходника; исправлять **только `co-va/professional/staging`**. Если выявлена необходимость менять серверный контракт, оформить **CORE HANDOFF**, не вмешиваться в Core из этого этапа; User/main не изменять.
- На каждую найденную проблему: одно адресное исправление → сценарий сбоя → регрессия связанных принятых сценариев → проверка фактического развёртывания → приёмка. Тесты/эталон/SHA не переписывать ради прохождения.
- Факт «нет воспроизводимых дефектов по утверждённой матрице» достаточен для приёмки; абсолютную гарантию отсутствия будущих ошибок не заявлять. Для каждого `locked` сохранить границы, доказательства и проверяемый базовый SHA.
- Начало исполнения: **шаг 0 и затем шаг 1 (День/шкала)**, прежде чем приступать к визуальным изменениям других режимов. Этот раздел — маршрут, не отчёт о пройденных тестах.
