# Карта закрытия продукта: от F-контейнера до действия

**Состояние:** рабочая карта для исполнения, все элементы стартуют с «Не принято». Ни один технический статус ниже не означает, что тариф разрешает доступ или что функция имеет `AdminToolReadiness=READY`.
**Источник структуры:** `co-va/core/BUSINESS_ARCHITECTURE.md` (F / E / режим / capability).
**Машинный реестр:** `RELEASE_CLOSURE_REGISTRY.json`. Одна и та же запись не должна отдельно существовать в нескольких не связанных таблицах.
**Защита:** `scripts/release/verify-closures.mjs`. Не CI, не серверная функция и не новая UI-библиотека.

## 1. Как читается карта

| Уровень | Что означает | Что именно нужно закрыть |
| --- | --- | --- |
| **Тарифный релиз** | Start, затем Start+, затем Pro — *техническая программа выпуска*, не право доступа | Все включённые в выпуск бизнес-сценарии; отдельная матрица коммерческих прав Core |
| **F — контейнер** | Главная рабочая карта, например Журнал | Навигация, все предусмотренные режимы и возможности, правильный UI и данные |
| **E — инструмент** | Самостоятельная работа внутри F, если действительно существует | Собственный рабочий процесс, история, управление; без придуманной второй E |
| **Режим** | Способ увидеть одни и те же объекты, а не E | Представление, переключение, фильтрация, одинаковое состояние данных |
| **UI-компонент** | Мини-карта, список, календарь, Z/Q/X, кнопка | Единственный владелец, точный эталон формы, читаемость, размеры, поведение, мобильность |
| **Capability / действие** | Создать, перенести, оплатить, вернуть, продать | Реальная операция с подтверждённым сохранением, ошибками, повтором и историей |
| **Домен/API** | Record, Time, Finance и другие владельцы данных | Корректная транзакция, безопасность, единые факты, отсутствие вторых источников |

**Уровни не подменяют друг друга:** Журнал — F; День, Месяц, Список — режимы; График — подрежим Месяца; создание записи и оплата — capabilities. Никакой новой E для режимов Журнала.

## 2. Пример заполненной структуры: Start → Журнал

```text
START — технический выпуск
└── ЖУРНАЛ [F]                                         НЕ ПРИНЯТО
    ├── ДЕНЬ [режим]                                  НЕ ПРИНЯТО
    │   ├── Шкала/слоты [общий UI + Time]             НЕ ПРИНЯТО
    │   ├── Запись [capability]                       НЕ ПРИНЯТО
    │   │   └── Мини-карта [общий UI]                 НЕ ПРИНЯТО
    │   ├── Событие [capability]                      НЕ ПРИНЯТО
    │   └── Заметка [capability]                      НЕ ПРИНЯТО
    ├── МЕСЯЦ [режим]                                 НЕ ПРИНЯТО
    │   └── ГРАФИК [подрежим, НЕ E]                   НЕ ПРИНЯТО
    ├── СПИСОК [режим]                                НЕ ПРИНЯТО
    └── ОПЛАТА ЗАПИСИ [capability + Finance]          НЕ ПРИНЯТО

Другие обязательные контуры технического выпуска Start:
Профиль / Сервис / Контакты / Продажа вне записи / Финансы.
Они НЕ автоматически объявляются включёнными в коммерческий тариф Start.
```

Общие компоненты `miniCard`, Calendar, List, Z/Q/X и общие домены Record/Time/Settlement показаны в реестре **отдельными ссылками**, а не размножаются в каждой карте. Если общий компонент изменился, затронутыми считаются все закрытые сценарии, которые от него зависят.

## 3. Статусы без ручных пользовательских «галочек»

- **Не принято (`open`):** код может уже существовать и даже иметь отдельные зелёные тесты, но полная приёмка не доказана.
- **В проверке (`verifying`):** исполнитель сопоставляет реальный UI, бизнес-операцию и сервер на тестовой среде.
- **Закрыто (`locked`):** реальные сценарии и внешний вид приняты, сохранены доказательства и точная версия Git. Изменения без отдельного решения владельца не допускаются.

**Родитель нельзя закрыть, если не закрыты все обязательные дочерние элементы и зависимости.** Это вычисляемое правило — вручную статус контейнера «Готово» ставить недостаточно.

**Критерии по каждому элементу:**
- **Визуальный:** пользовательски утверждённый эталон, без произвольной стилистики, дублей и лишних заголовков.
- **Интерактивный:** все предусмотренные действия реально работают; скролл/клавиатура/жесты не сдвигают Z/Q/X.
- **Данные:** тот же факт виден во всех режимах и после повторного входа, нет ошибок и ложных подтверждений; пробный платёж не дублируется.
- **Регрессионный:** сохраняется адресный проверочный сценарий с ожидаемыми результатами. Это **не** новый CI.

**Эталон нельзя определять наугад только потому, что в CSS уже есть число или размер.** Если карточка в User и Professional различается, сначала выясняется, какой вид согласован, и только затем делается точечная замена.

## 4. Что происходит после закрытия

1. Исполнитель фиксирует в реестре `locked`, основание пользовательской приёмки, дату, Git SHA и доказательства: снимки результата, выполненный сценарий, проверенную версию Core/API. Для UI необходимо подтверждение внешнего вида на устройстве.
2. При следующей работе исполнитель запускает короткую сверку: `node scripts/release/verify-closures.mjs`. Она проверяет дерево статусов и сравнивает изменённые файлы с сохранённым SHA закрытого элемента. Для Core и User нужен также отдельный осмотр их изменений и согласованных API — этот скрипт не имеет доступа к их локальным деревьям.
3. Если изменён файл или зависимый общий UI, используемый закрытым элементом, работа **останавливается до определения влияния**. Без отдельного согласования владельца менять этот контракт нельзя. После разрешённого изменения повторно выполняется только затронутый сценарий и заново фиксируется его эталон.
4. Проверки нельзя «чинить» переписыванием их ожидаемого результата. Правка теста, эталона, разрешённых зависимостей или замороженного SHA — **отдельное изменение контракта**, а не часть обычной разработки.
5. Перед релизом Start выполняется общий прогон Start; перед Start+ — Start и Start+; перед Pro — все три уровня. Не на каждый коммит. Никаких новых GitHub Actions.

## 5. Граница технической защиты

Скрипт — **обнаружение вмешательства**, не физический запрет записи в Git. Сейчас нет подтверждённого доступа к настройкам защиты веток GitHub (API вернул `403`), поэтому нельзя заявлять, что GitHub уже не пропустит изменение. Для **необходимого технического запрета** нужна настройка GitHub ruleset/защиты `main` с разрешением владельца на изменение замороженных контрактов; это отдельный доступ и отдельная настройка, она не требует нового CI, но может потребовать человеческого согласования таких PR.

До появления серверной защиты любой исполнитель обязан соблюдать эту карту; реальные ограничения должны подтверждаться на GitHub, а не обещанием другого чата. Изолированные тесты и запись в документе не гарантируют, что баг больше никогда не возникнет.

## 6. Что исполняем первым

**Журнал → День.** В текущей кодовой базе его владелец — `journal/день.js`, шкала — `ui/time/journal-day.js`, Record — `core/records/view.js`; интерфейсные зависимости отмечены в JSON. Проверяем связку формы, жестов, действий и данных; замечания исправляем по одному подтверждённому несоответствию. После адресной проверки закрываем только то, что действительно доказано. Пока `День` не принят, весь `Журнал` и технический Start остаются открыты.

**Стадия исполнения на дату создания:** реестр и ручная защита подготовлены, **ни одного закрытого элемента не объявлено**. Код Журнала и другие приложения этим документом не меняются.
