Статус: требования установлены по действующим исходникам Professional/staging и Core/main; загрузчик не реализован. Этот файл не подтверждает готовность.
Источник структуры: `core/loyalty/deposit/index.js::openCreateProgramQ`, `core/loyalty/deposit/card-presentation.js::depositFundingProgress`, Core `server/src/finance/finance.service.ts::recordDepositFunding`, `server/src/loyalty/deposit.service.ts`, `server/src/loyalty/deposit-state.ts`.
При противоречии старых документов применять актуальные правила `PROJECT_STATE.md` от 23.11.2026: истечение срока не обнуляет остаток.

## 1. Пользовательский формат
- Один XLSX, **один лист**, одна строка = один факт пополнения или исторического списания; **нет** обязательной отдельной строки создания программы/выдачи карты, нет действия «первое пополнение».
- Одна визуальная таблица с группами колонок: **Депозит / Человек / Операция**. Группы различаются шапкой, а не разными листами или режимами импорта.
- Программа создаётся при первом обнаружении заполненных условий и подходящей денежной операции, если не существует; отдельная карточка человека открывается только **положительным пополнением**.
- В повторных строках программы достаточно названия и, при неоднозначности, UEI/ключа программы. Условия наследуются из первой заполненной строки или уже существующей программы. Отсутствующие значения не заменять случайными настройками.
- Импорт целиком либо по «С — По» на дате фактической операции. Перед применением — предпросмотр с ошибками и с указанием создаваемых и существующих объектов. Никаких реальных изменений при предварительной проверке.

## 2. Поля блока «Депозит» — соответствие реальному редактору
| Столбец Excel | Модель / допустимые значения | Правило |
|---|---|---|
| Депозит | `name` | Название, обязательно для ссылки на программу |
| UEI программы | отдельный реестр UEI, 4 символа | Опционально для переноса; если нет, приложение создаёт уникальный UEI через штатный механизм, не допускает конфликтов |
| Вид суммы | `amountMode`: `fixed` / `free` | Фиксированная / Свободная |
| Номинал | `amount` | Только для `fixed`, положительный; для `free` не требовать |
| Срок | `termMode`: `indefinite` / `dated` | Бессрочно / Период |
| С | `termStartDate` | Обязательно для `dated`, календарная дата |
| По | `termEndDate` | Обязательно для `dated`, конец дня **включительно** |
| Выгода | `benefitType`: `none` / `discount` / `accrual` | Нет / На обслуживание / Начисляется сразу |
| Выгода, % | `benefitValue` | 0..100; требуется положительное число при `discount` / `accrual` |
| Условия | `description` | Необязательный текст условий |
| Показать | `showToAll` | Настройка видимости программы; не влияет на право/бизнес-расчёт |

Не добавлять вымышленных режимов срока, выгоды, процентов или номинала. `benefit` и `termRule` — производные подписи UI. `status`, `cardSequence`, скидки, суммы «Внесено / К оплате / Списано / Остаток» система формирует автоматически.

**Идентичность программы.** Совпадение только названия недостаточно для программ с разными условиями/периодами. Совпадение UEI или стабильного идентификатора + полных условий допускает повторное использование; одинаковые имена с несовместимыми условиями — конфликт на предпросмотре, а не объединение. Условия ранее оформленного депозита иммутабельны.

## 3. Поля блока «Человек»
- Контакт: идентификатор/UEI и/или телефон, имя для просмотра. Сопоставлять с реальными Контактами; неоднозначность отправлять на сверку, не приписывать чужому человеку.
- Необязательный внешний номер/ключ **конкретной карты депозита**: позволяет различать несколько депозитов одной программы у одного человека; без него неоднозначные случаи блокировать, а не сливать в один.
- Лист не содержит отдельной операции «выдача» или нулевого открытия.

## 4. Поля блока «Операция»
- **Дата** фактического события `occurredAt`, отдельно от системного времени внесения `recordedAt`; нельзя автоматически заменять вчерашний перевод датой импорта.
- **Действие**: `Пополнение`, `Списание` (только исторический факт без создания Журнала). Не требовать «первое/второе».
- **Сумма**: положительная величина; знак определяется действием.
- **Кошелёк**: при поступлении сопоставить с реальным кошельком приложения. Если неизвестен — **не блокировать импорт депозитной истории**: сервер фиксирует пополнение в Core FinanceOperation, увеличивает остаток депозита и помечает `walletResolution=unknown`, но **не создаёт кассовую проводку** до выбора кошелька. Не подменять «Наличными». Когда кошелёк указан позже, привязать его к той же операции без повторного поступления.
- **Описание**: произвольное пояснение списания, например название услуги, **без автоматического создания записи в Журнале**.
- **ID исходной операции** (необязательно, но рекомендуется): для защиты от повторного импорта. При его отсутствии одинаковые суммы и даты не доказывают идентичность — сомнительные повторы на сверку.
- При наличии факта возврата он должен использовать существующий отдельный контракт возврата/закрытия, а не маскироваться под списание за услугу.

## 5. Правила переноса
1. Фиксированная сумма: `К оплате = max(0, номинал - суммарное внесено)`; свободная сумма: нет задолженности по номиналу. `К оплате` не тождественно доступному остатку.
2. Первое фактическое пополнение создаёт конкретную карту сразу с ненулевым остатком. Последующие пополнения — тот же объект в пределах его однозначной идентичности.
3. `discount` уменьшает цену подходящей услуги, но не начисляет денежный бонус. `accrual` увеличивает `benefitBalance` согласно действующему Core.
4. Контроль хронологии: срок действия для каждой операции, наличие предыдущих денег, отрицательные остатки в любой точке и невозможность двойного расходования. Истёкший депозит имеет статус «Списан», но исторический неиспользованный остаток не обнуляется.
5. **Историческое списание без записи Журнала** требует отдельной корректной серверной операции с неизменяемой историей и защитой от повторного списания. Нельзя выдать за готовое: текущий Core FinanceOperation использует `payment` для настоящих записей и пока не содержит полной договорённой операции импортированного списания без записи. Позднейшая привязка визита не должна списывать повторно.
6. Происхождение каждой операции фиксируется в каноническом Core FinanceOperation: `origin=application` либо `origin=excel_import` **отдельно** от действия, даты, суммы и статусов. Хранить фактическую `occurredAt` отдельно от серверной даты регистрации `recordedAt`; импорт несёт идентификатор внешней операции и пакета. История API возвращает отдельные `balanceAfter`, `walletResolution` и `reconciliationStatus`. Импортированное списание без Record позже связывается с записью без повторного расходования. Единственный нормативный финансовый журнал — Core FinanceOperation; дополнительный Excel-журнал запрещён.
7. Все изменения — только после явного «Применить», со строгой проверкой и изоляцией tenant, атомарностью подтверждаемой группы, идемпотентностью и отказом от частичного молчаливого импорта.
8. Не затрагивать User и Professional/main; разработка UI — Professional/staging, API/ledger — Core отдельным проверенным изменением. Не объявлять готовым до работающего импорта и приёмки.

## 6. Тестовый минимум до «Готово»
Фиксированный/свободный номинал; без выгоды/скидка/начисление; бессрочно/срок «С — По» (включая последний день); разные клиенты одной программы; одинаковые названия с разными условиями; несколько карт одного человека; частичные внесения и закрытие номинала; точная фактическая дата; исторические списания и последующие остатки; истечение срока без обнуления; неизвестный кошелёк; неизвестный Контакт; повторная загрузка; диапазон дат; отсутствие операций Журнала; формат/ошибка XLSX.
