## Склад: единицы «шт.» и «уп.» — обязательное правило владельца (16.11.2026)

- **«шт.» — одна самостоятельная физическая единица**: один флакон шампуня, один тюбик краски, одна машинка. Флакон объёмом 980 мл — **1 шт. с номиналом 980 мл**, а не «упаковка 980 мл».
- **«уп.» — единица прихода/фасовки**, а не физический флакон или тюбик. В ней могут быть **несколько отдельных штук** (10 ампул, 100 перчаток) или **измеряемое содержимое фасовки** (5 кг земли, 900 г пудры). **«шт.» и «уп.» не взаимозаменяемы**: один флакон шампуня остаётся 1 шт., даже если его номинал 980 мл.
- **«В упаковке»** — одно поле «число + единица»: **10 шт.** для групповой упаковки либо **5 кг / 900 г / 1 л** для фасовки. Если выбраны штуки, дополнительный **номинал одной штуки** (например, 5 мл на ампулу) необязателен; если фасован весовой материал, второго номинала нет. Для прихода **«шт.» поле «В упаковке» скрыто**.
- **Номинал одной штуки** — отдельная характеристика её содержимого: например, каждая из 10 ампул содержит 30 мл. На одну ампулу можно списать **1 шт.**, либо расходовать из неё **30 мл** (или часть объёма), если выбран расход по мл и известен пересчёт. Число ампул в упаковке (10 шт.) никогда не заменять объёмом содержимого (30 мл на ампулу).
- **Приход, расход, продажа и наценка** обязаны сохранять разницу единиц. Цена одной «шт.» из многоштучной «уп.» вычисляется по фактическому числу штук внутри, а не по полной цене упаковки. Не подставлять коэффициент 1:1 для «уп.» → «шт.» без фактической конверсии.
- Это нормативное решение владельца, **не подтверждение, что каждый существующий сценарий кода уже валидирует правило**. Перед новыми исправлениями проверить реализацию и данные; не вводить глобальную миграцию или серверные изменения молча.

## Склад: ресурс многоразовой штуки — правило владельца (16.11.2026)

- Пример: **1 пилка = 3 процедуры**, упаковка = 10 отдельных пилок. Количество ресурса задаётся для **одной штуки**, а не для всей упаковки.
- Удалить поле **«Списать после ресурса — 1 шт.»** из Q редактора: у пользователя нет обязанности вычислять число списываемых пилок. При выборе **«По окончании: Списать»** одна исчерпавшая ресурс штука списывается автоматически. При 4 процедурах: 1 пилка списана, вторая использована на 1/3 и имеет 2 применения до списания; при 6: списаны 2 пилки.
- Серверный `recordResourceUse` уже вычисляет полные циклы как `floor((progress+quantity)/resourceLimit)` и сохраняет остаток цикла в `InventoryResourceProgress`; единица списания на полный цикл фиксируется клиентом как `resourceStockQuantity: 1`, без отдельного поля UI.
- **Статус:** UI поле удалено в Professional/staging; отправку фактических событий `POST /inventory/resource-uses` из рабочих процессов ещё не подтвердили. Не объявлять автоматический учёт использования в Journal действующим до сквозной проверки.
- Не смешивать ресурс одной штуки и количество штук в упаковке; не добавлять обратно ручной выбор «сколько штук списать после ресурса».

## Склад: цепочка прихода → одной штуки → расхода (16.11.2026)

- Последовательность в Q: **наименование → единица прихода (шт. / уп.) → содержимое упаковки (только для уп.: число шт. или масса/объём фасовки) → номинал одной физической штуки (только если он нужен) → удобный расход (шт., мл, г, кг или л)**. Цена закупки относится к единице прихода. Человек может сохранить товар без номинала, тары, цены и нормы расхода.
- **«Шт.» в приходе** — одна самостоятельная единица (флакон, тюбик, баллон, кресло): отдельного поля количества нет. **«Уп.» в приходе** — несколько отдельных штук (с дополнительным необязательным номиналом одной штуки) **либо фасованное весовое/жидкое содержимое** (без второго номинала). «Уп.» запрещено в номинале одной штуки и в селекторе списания. Для новой карточки единица списания по умолчанию следует заданной измеряемой характеристике, а ручной выбор не перезаписывается.
- Пример ботокса: **10 ампул в упаковке, 5 мл в каждой**. Если расход — «шт.», **1 шт. = 1 ампула = 5 мл**, списание штуками; если расход — «мл», автоматический пересчёт из 5 мл на штуку (вся упаковка = 50 мл). Нельзя подменять число 10 объёмом 5 или 50.
- Если расход задаётся в **«г»**, а номинал задан в **«мл»**, нельзя считать миллилитры равными граммам. Требуется фактическое нетто одной штуки, полученное по брутто/таре (или подтверждённое нетто без тары). Тогда **1 штука = измеренное нетто в граммах**; для упаковки граммовый эквивалент умножается на число штук.
- Существующий API `packageQuantity` хранит рассчитанное количество **базовых единиц учёта на одну единицу прихода**, а не второе ручное поле «номинал упаковки». Переход от штуки к измерению хранится как явный `conversionRules`. На клиенте не добавляется второй физический номинал. Для ранее созданных карточек число штук восстанавливается только из однозначно известных данных, без догадок.
- **Реализация:** Professional/staging Q переделан без нового UI-компонента: уп. может означать группу штук или измеряемую фасовку. Неизвестную массу тары, нетто, норму расхода и цену можно оставить пустыми и создать позицию. Для новой позиции открыта минимальная группа; остальные разделы раскрываются при необходимости. Критический и желаемый запас имеют независимую явно выбранную единицу; число 1,05 не округляется. В штатном Q движения добавлены «Дата прихода» / «Дата окончания» для реального учёта событий. Проверено по исходникам и изолированным расчётам; iPhone, API и автоматическая аналитика использования по услугам ещё не подтверждены.

## Обязательный контракт Professional

- Единственный владелец Professional application: `co-va/professional`.
- Рабочая ветка исполнителя только `staging`. `main` не менять в рамках этой карты. Новые рабочие ветки не создавать.
- `co-va/core` не является frontend/runtime/build dependency Professional. Из Professional в Core не переносятся и в Core не изменяются файлы в ходе этой работы.
- Core остаётся владельцем backend/API/server logic/Prisma/PostgreSQL и общих серверных контрактов.
- Любая необходимость изменить Core фиксируется только как `CORE HANDOFF` и выполняется позднее отдельным единым этапом вне этой карты.
- Professional работает с сервером только через утверждённый API-контракт. Прямого доступа браузера к БД/Prisma/серверным внутренностям быть не должно.
- Локальная папка `core/**` внутри `co-va/professional` — клиентский доменный слой; она не означает зависимость от репозитория `co-va/core`.
- Замена выполняется вместо старой реализации, а не поверх неё. Legacy/compat/bridge/fallback/duplicate UI после замены удаляются.
- Утверждённый Shared UI в `co-va/user` является эталоном общего UI-контракта. Professional не создаёт второй UI-мир.
- Shared внутренние события в Professional не получают маркер конкретного приложения; для общего UI используется нейтральный namespace.
- Public Booking остаётся отдельной guest surface и не смешивается с Professional App Runtime.
- Постоянный CI не должен управлять незавершённой очисткой. Сначала архитектура и runtime доводятся до правильного состояния, затем подтверждается работа, и только после этого ставятся финальные guards/CI.
- Инфраструктурное подключение Amvera/доменов выполняется только после архитектурной очистки Professional.

## Цель

Сделать `co-va/professional` полностью самостоятельным Professional-приложением по тому же принципу чистоты, что и `co-va/user`:
- Professional frontend/runtime/UI живут только здесь;
- User/Admin/Landing и чужие runtime-контуры отсутствуют;
- общий UI не дублируется;
- Professional не зависит от frontend/runtime `co-va/core`;
- Core остаётся API/DB/server владельцем;
- после доказанной самостоятельности отдельным будущим этапом из Core удаляется оставшийся Professional frontend/runtime.

## 2026-11-15 — Заказ поставщику: правильный сохраняемый документ

- В Z2 производителя штатное `initV2ListReorder` снова подключено при `position-asc`, отсутствии поиска/фильтров и не менее двух пронумерованных товаров; ручки drag выводятся у пронумерованных. Список теперь содержит все товарные строки внутри одного общего `.list-entries`, поэтому Core `POST /inventory/items/reorder` получает **полный порядок ID компании**; после ответа перерисовывается только список Z2 с новыми номерами и правильно расположенными заголовками. Для Z2, открытого из нестандартной первой группы (не Производитель), drag выключен, поскольку Core reorder-scoping по `manufacturer`; пользовательские данные не переписываются.
- Тесты: JS syntax PASS; 10/10 сценариев отображения списка в сохранённом порядке, повторных заголовков, отсутствия незапрошенной перестановки, единый V2 list, drag у пронумерованных, без drag при поиске, отсутствие других производителей; 6/6 сценариев callback drag, сохранения позиций в mock, повторной привязки обработчиков. ## 2026-11-20 — Утверждённая группировка склада: фиксированный производитель, упорядоченные уровни

- **Решение владельца:** «Производитель» — неизменный первый/корневой уровень, отдельный V2-список производителей. В интерфейсе больше нельзя удалять, переименовывать или перемещать этот критерий; значения производителей остаются редактируемыми. Остальные критерии — независимые пользовательские справочники; их названия не определяют уровни. Порядок критериев (кроме первого) задаёт иерархию. Профессионал может менять их порядок штатным drag-handle в Q «Группы».
- **Карточка товара:** фиксированный селектор «Производитель», затем только реально выбранные пары «группа → значение» и одна начальная пустая пара, если больше ничего не выбрано. Следующая пара добавляется лишь после заполнения предыдущей; можно выбрать любую ещё не выбранную группу, удалить назначение или пропустить промежуточный критерий без «пустого» уровня. Основной payload Core остаётся существующим: legacy manufacturer/category/productType и `criteriaValues` для дополнительных групп; данные не мигрировали.
