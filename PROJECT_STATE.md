## Обязательный вход для всех чатов — общий UI-контракт

- **Сначала прочитать:** этот `PROJECT_STATE.md`, затем единый [UI_ALPHABET.md](https://github.com/co-va/core/blob/staging/UI_ALPHABET.md) в `co-va/core/staging` (реальные UI-владельцы, стабильные ID, межрепозиторные зависимости, критерии приёмки), затем применимые существующие карты и тесты. При отсутствии доступа к любому источнику не выдавать предположения за проверенные факты.
- **Перед изменением UI:** назвать контрактный ID, найти его реальные реализации и потребителей в User / Professional / Admin, проверить расхождения и существующие утверждения; **не** создавать второй UI, вторую карту или новые ID для одного компонента.
- **Границы:** `co-va/core` — API/Администратор/центральный UI-контракт; `co-va/user` — User; `co-va/professional` — Professional. Нельзя редактировать чужой репозиторий и `main` без отдельного разрешения; рабочие правки только в `staging`.
- **Текущее исполнение:** Работать с frontend Professional. Для статусов приёмки читать существующие RELEASE_CLOSURE_MAP.md и RELEASE_CLOSURE_REGISTRY.json; не создавать второй статусный реестр. Существующие проектные и релизные планы не заменять новыми. Любые статусы «утверждено»/«закрыто» — только по доказательствам, отдельно визуал и функциональность.
- `AGENTS.md` — короткая входная точка для нового исполнителя. Защита GitHub и реальное совпадение UI **не** считаются обеспеченными этим текстом.

## Обязательный контракт Professional

- Единственный владелец Professional application: `co-va/professional`.
- Рабочая ветка исполнителя только `staging`. `main` не менять в рамках этой карты. Новые рабочие ветки не создавать.
- `co-va/core` не является frontend/runtime/build dependency Professional. Из Professional в Core не переносятся и в Core не изменяются файлы в ходе этой работы.
- Core остаётся владельцем backend/API/server logic/Prisma/PostgreSQL и общих серверных контрактов.
- Любая необходимость изменить Core фиксируется только как `CORE HANDOFF` и выполняется позднее отдельным единым этапом вне этой карты.
- Professional работает с сервером только через утверждённый API-контракт. Прямого доступа браузера к БД/Prisma/серверным внутренностям быть не должно.
- Локальная папка `core/**` внутри `co-va/professional` — клиентский доменный слой; она не означает зависимость от репозитория `co-va/core`.
- Замена выполняется вместо старой реализации, а не поверх неё. Legacy/compat/bridge/fallback/duplicate UI после замены удаляются.
- Утверждённый Shared UI в `co-va/user` является эталоном общего UI-контракта. Professional не создаёт второй UI-мир.
- Shared внутренние события в Professional не получают маркер конкретного приложения; для общего UI используется нейтральный namespace.
- Public Booking остаётся отдельной guest surface и не смешивается с Professional App Runtime.
- Постоянный CI не должен управлять незавершённой очисткой. Сначала архитектура и runtime доводятся до правильного состояния, затем подтверждается работа, и только после этого ставятся финальные guards/CI.
- Инфраструктурное подключение Amvera/доменов выполняется только после архитектурной очистки Professional.

## Цель

Сделать `co-va/professional` полностью самостоятельным Professional-приложением по тому же принципу чистоты, что и `co-va/user`:
- Professional frontend/runtime/UI живут только здесь;
- User/Admin/Landing и чужие runtime-контуры отсутствуют;
- общий UI не дублируется;
- Professional не зависит от frontend/runtime `co-va/core`;
- Core остаётся API/DB/server владельцем;
- после доказанной самостоятельности отдельным будущим этапом из Core удаляется оставшийся Professional frontend/runtime.

## Финансы → Кошельки: предотвращение потери каталога при открытии — 2026-11-08

- **Критичный дефект устранён**: `core/finance/cash/data.js::getWallets()` раньше при пустом локальном состоянии автоматически вызывал `write(SYSTEM_WALLETS)`. Если `loadBusinessState()` уже включил серверную очередь, а `loadAuxiliaryState()` ещё не вернул реальные кошельки, это могло отправить `PUT /auxiliary-state/wallets` с одним системным набором и полностью заменить сохранённые Сбербанк/Тинькофф/тестовые кошельки. Такой путь возможен при `Клиент → Программы → Депозит`, потому что scope `people` не включает wallets, а исходная депозитная форма вызывает `getWallets()`. Это **возможное объяснение**, не подтверждённое чтением реальной БД.
- Теперь `getWallets()` строго read-only, **ничего не сохраняет**, в состоянии до загрузки не показывает ложную пару системных кошельков. `write()` запрещает любые изменения до серверной гидратации. Два системных кошелька добавляются в вывод как виртуальные значения и сохраняются только вместе с явной корректной пользовательской операцией. При logout cache/готовность сбрасываются.
- `core/runtime/auxiliary-state.js` не подменяет каталог пустым при неверном поле в ответе API; `core/runtime/server-sync.js` не затирает кэш при отсутствии массива `wallets`. `issueDepositForPerson()` до открытия родной Q оплаты теперь явно загружает `loadAuxiliaryState('loyalty')`, содержащий реальные wallets.
- Изолированные тесты: до гидратации чтение не отправляет PUT; ранняя запись блокируется; серверный каталог из четырёх кошельков сохраняется целиком; повторное чтение без PUT; пустой серверный каталог отображает виртуальные дефолты без PUT; явное создание кошелька отправляет полный набор — 6/6 PASS.
- **ВНИМАНИЕ: это предотвращает новые потери, но не восстанавливает уже перезаписанные данные**. Реальный статус `BusinessAuxiliaryState.data.wallets` и резервные копии БД можно проверить только с авторизованным доступом к production tenant. Существующие `FinanceLedgerEntry` содержат `walletId` и часто `walletName`: идентификаторы оплаченных кошельков могут быть восстановлены из этих фактов, даже если сам каталог перезаписан; кошельки без операций потребуют архивной копии. Не вносить восстановление вслепую и не создавать новые ID вместо старых.
- Все изменения только `co-va/professional/staging`. `co-va/core` и `main` не изменялись. Реальные данные пользователя и Amvera пока не проверены.

## Person Q save / iOS Safari `Load failed` — 2026-11-09

- На iPhone в Z2 клиента показывалось системное уведомление `Не удалось сохранить — Load failed`. Его открывает глобальный слушатель `professional:business-persistence-error` в `professional/workspace.js`, а не сам рендер Z2. Это ошибка очереди серверных мутаций; `Load failed` в iOS Safari — сбой `fetch` без HTTP-ответа, а не доказательство неверных полей анкеты.
- В `core/business-persistence.js::send()` **любая** нормальная JSON-запись отправлялась через `fetch(...,{keepalive:true})`. Для keepalive-запросов браузеры ограничивают объём отправляемого тела (около 64 KiB). При повторной отправке объекта человека с фото (возможен большой data URL) WebKit может отвергнуть запрос с `Load failed`. Удалён принудительный `keepalive`: все текущие запросы посылаются обычным авторизованным `apiRequest`, очередь повторов сохраняется. Ошибка fetch теперь объясняет тип операции, отсутствие ответа от сервера и факт повторной отправки вместо голого `Load failed`.
- В `core/people/people.js::openPersonEdit()` ранее Q `Данные клиента` закрывалась сразу после локального `savePeople()`, не дожидаясь серверного ACK; при ошибке пользователь видел внешнюю ошибку уже на Z2. Теперь кнопка Save блокируется на время отправки, `isBusinessServerReady()` проверяется, `flushBusinessPersistence()` обязательно завершается до закрытия Q и обновления Z2. При ошибке Q остаётся открытой с сохранённым вводом и сообщением.
- Проверены посредством исполнения реального JS модуля очереди с мок-сервером и большого тела `>100 KB`: без keepalive; первичный `TypeError('Load failed')`, повтор и успех; корректный текст ошибки и очистка состояния; одно событие успешной партии. Проверено расположение `await flushBusinessPersistence()` до `v2Close` и blocking action — 7/7 PASS. Синтаксис затронутых JS модулей — PASS.
- Только `co-va/professional/staging`; `co-va/core` и `main` не менялись. Live Safari/Amvera запрос и реальная запись человека в PostgreSQL на iPhone здесь не проверены; если сообщение повторится, проверять доступность API и точный проблемный PUT, не менять схемы данных вслепую.

Источник депозита учитывает `status=active` и реальные даты действия условий; по окончании программы перестаёт действовать без изменения личных данных.
- `core/people/people.js` → Q «Данные клиента»: `Скидка %` показывает **20** (или другой фактический процент) при активном программном источнике и становится `disabled`. Перед разрешением редактирования происходит `listPersonDeposits(person.key)` — обязательная сверка с сервером; пока проверка не завершилась, поле и сохранение заблокированы. При ошибке сетевой проверки Q остаётся открытой, сохранение запрещено с причиной. После завершения программы поле показывает индивидуальную скидку (если задана) или пустое значение и снова доступно для редактирования.
- При сохранении остальных данных клиента скидка программы не переносится в поле `discountPercent`; сохранение индивидуального процента разрешено только без действующей программной скидки, повторно проверяется перед `savePeople`. `formSnapshot` отделяет программное (неизменяемое) отображение от настоящих ручных изменений, чтобы загрузка процента не превращалась в ложную правку.
- `core/people/card-presentation.js` отображает **один эффективный процент** скидки на самой карточке клиента (не только в редакторе), используя тот же расчёт.

## Скидка: единый источник от клиента до оплаты — 2026-11-09

- **Бизнес-правило:** либо индивидуальная скидка `Person.discountPercent` (редактируемая), либо действующая скидка одной назначенной программы (процент берётся из программы и не редактируется). Не переносить процент программы в личную скидку: иначе возникают два источника и ошибка задвоения.
- Карточка клиента, Q «Данные клиента» и карточка записи используют общий `getPersonPriceCondition` и прежний `resolvePersonPriceCondition`. При действующем депозитном проценте поле клиента показывает, например, 20% в заблокированном виде; после окончания программы возвращается свободный личный процент.
- **Исправлен прежний разрыв:** `core/finance/settlement.js::recordSettlementPriceCondition` теперь автоматически применяет единственный активный источник `type='program'` к **неоплаченной** записи, даже если в самой записи не выбирали программу повторно. При явно выбранном депозите проверяет, что конкретное назначение ещё активно; просроченный депозит не даёт замороженных 20%. Иные явно выбранные типы программ не менялись.
- `core/payment/procedure-adjustment.js` уже блокировал редактирование обоих полей скидки для programPercent. Теперь в `core/records/records.js::openProcedureAdjustment` до показа редактора обязательно `listPersonDeposits(personKey)`, и вследствие корректного Settlement блокировка действует при **автоматически** назначенной программе. При личной скидке процент идёт как редактируемая коррекция цены.
- `core/records/view.js` показывает состояние проверки до первой отрисовки сумм записи и обновляется после загрузки действующей программы. На карточке записи показан эффективный процент, а не только `person.discountPercent`. `core/people/record-creation.js` при создании из контакта тоже заранее загружает программу.
- `core/payment/record-payment.js::openPaymentEntry` открывает X мгновенно, но **не** показывает ошибочный `К оплате` до серверной проверки условий; при ошибке проверки оплату не запускает. Перед фактическим проведением повторно проверяет статус депозита, процент, итоговую сумму и оплаченное; при изменении требует заново открыть оплату. Сохранённая историческая Finance Settlement, по которой уже есть движения, **не пересчитывается** при последующем назначении/истечении программы.
- Регрессионный исполняемый тест `scripts/ci/record-discount-smoke.mjs`: назначенная программа 20% автоматически уменьшает 50 000 → 40 000, запрещает ручную коррекцию; ручные 12% дают 44 000 с разрешённым редактированием; истечение возвращает обычную цену; ранее проведённые платежи остаются историческими; выбранный просроченный депозит не даёт скидку; источники и preflight проверяются. Изолированный тест PASS, синтаксис всех изменённых файлов PASS. **Живое проведение оплаты и iPhone не тестировались.**
- Только `co-va/professional/staging`; `co-va/core` и `main` не менялись. Не переписывать программу/Settlement или вторично сохранять процент в Person.

### 2026-11-12 — Физические тюбики и граммы, склад (staging)
