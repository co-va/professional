# CORE HANDOFF — продукт, остатки и цены по местам покупки

Статус: **требуется отдельная реализация в `co-va/core`**. Этот файл находится только в `co-va/professional/staging`. Сам Core не изменялся.

## Утверждённая предметная модель

1. **Продукт (`InventoryItem`)** — сущность и характеристики независимо от остатка: производитель, название, тип, единица учёта/расхода (`unit`), номинал упаковки (`packageQuantity`), масса брутто/тары, артикул, штрихкод, правила использования (`canConsume`, `canSell`).
2. **Движение (`InventoryMovement`)** — приход, расход, продажа, возврат, списание или корректировка. Только движения влияют на остаток. Создание карточки продукта не создаёт приход.
3. **Остаток (`balance`)** — производный результат движений, только для чтения в карточке продукта.
4. **Места покупки / предложения поставщиков (`InventorySupplierOffer`)** — множественные независимые предложения для одного продукта; магазин и поставщик здесь равноправные источники приобретения, каждый со своими условиями и ценой.
5. **Базовая цена продукта** — ориентир/номинальная цена, которую задаёт пользователь независимо от последней закупки и от предложения любого поставщика.

## Что уже есть

- `GET /inventory` возвращает `items[].balance`, `lastPurchasePrice` и массив `supplierOffers`.
- В Prisma существует `InventorySupplierOffer`: `supplier`, `listPrice`, `discountPercent`, `actualPrice`, `supplierSku`, `note`, `isActive`.
- `POST /inventory/items` и `PUT /inventory/items/:itemId` сохраняют характеристики продукта. При `quantity > 0` создание товара пока автоматически создаёт «Начальный остаток»; Professional с этого этапа **не передаёт количество**.
- `lastPurchasePrice` не является независимой базовой ценой: она может изменяться при поступлении.
- Отдельных REST-операций для создания, изменения и архивирования `InventorySupplierOffer` нет. Импорт в сервисе существует, но не является публичным CRUD-контрактом.

## Необходимый API-контракт (к отдельной реализации в Core)

1. Добавить **независимую справочную цену за номинальную упаковку** (например, `referencePrice`) в `InventoryItem`: nullable, >=0; поддержка в создании, редактировании и `GET /inventory`. Не подменять ею `lastPurchasePrice`.
2. Ввести tenant-scoped CRUD для предложений конкретного продукта, например:
   - `POST /inventory/items/:itemId/offers` — создать;
   - `PUT /inventory/items/:itemId/offers/:offerId` — изменить;
   - `DELETE /inventory/items/:itemId/offers/:offerId` — деактивировать, **без удаления исторических закупок**.
   Поля: название места покупки / поставщика, прайс, скидка, итоговая цена, артикул поставщика, примечание; `offerId` стабилен.
3. **Цена предложения должна иметь понятное основание.** Хранить количество базовых единиц учёта в одном предложении (`unitsPerOffer` или эквивалент), т.к. один источник продаёт упаковку 100 шт., другой — поштучно. Не смешивать стоимость упаковки с себестоимостью одной штуки/грамма/миллилитра.
4. При приходе выбранное предложение может подставить источник, цену и пересчёт в единицы учёта, но **фактическую цену партии надо фиксировать в движении/лоте**; будущие изменения прайса не должны менять историю. Пример: 2 флакона × 250 мл по 500 ₽/флакон = приход 500 мл с себестоимостью 2 ₽/мл.
5. Проверять в Core изменение `unit` для продукта с движениями: нельзя молча переинтерпретировать накопленный остаток из «г» в «шт.»; нужна миграция/явное преобразование либо запрет.

## Что уже сделано в Professional

- Создание по `+`: только данные продукта, без начального остатка и без ввода закупочной цены.
- Полное редактирование: тип, способ использования, номинал, единица учёта, прочие характеристики.
- Показ итогового остатка и последней цены для чтения; при наличии — показ существующих предложений поставщиков **только для чтения**.
- **Запись множественных цен поставщиков и справочной базовой цены НЕ реализована до API.** Не создавать второй источник данных в локальном хранилище, auxiliary state или UI-заглушках.

## Границы

Core меняется отдельным исполнителем/этапом. Professional работает только в `staging`; `main` не изменять без разрешения владельца. Shared UI/геометрия Z/Q/X/V не меняются. CI не добавлять на текущем этапе.

## 2026-11-17 — Выбор категорий прайса для «Моих остатков»

- В карточке контрагента бренды отображаются строками V2 с количеством **товарных позиций**, без учёта категорий. Нажатие на бренд открывает Q с нативными `details/summary` категориями; напротив каждой категории — число реальных товарных строк.
- Владелец запросил **слева от раскрываемой категории** существующий `compactCheck` (28×28): включение выбирает **все товары данной категории** для «Моих остатков», выключение отменяет выбор. Заголовка «Товары» и нового UI-компонента не создавать; чекбокс должен быть независим от раскрытия.
- **Сейчас реального серверного действия нет:** `GET /inventory/counterparties/:id/catalog` выдаёт прайс; `POST .../catalog/:rowId/link` связывает только готовую карточку с одним товаром; `POST /inventory/items` создаёт одну отдельную карточку и не является атомарной операцией выбора категории. Нет канонической группы, статуса включения, идемпотентного пакетного добавления / отмены, безопасного снятия выбора без потери движений.
- Требуется отдельный **Core** API: сохранение набора выбранных catalog-row IDs (или эквивалент связей), точный статус для чтения в Q, идемпотентная групповая операция и корректное поведение после обновления прайса. Нельзя массово создавать сомнительные карточки с выдуманными единицами и нельзя архивировать существующие товарные карточки/движения по снятию галочки. **Professional показывает компактные галочки только для временного выбора в Q**, с явным предупреждением «Выбор пока не сохраняется в остатках». При закрытии карточки временный выбор теряется; без Core API он не создаёт, не удаляет и не архивирует складские позиции.
- Только `Professional/staging` UI и документация о зависимости; Core, User, main и серверные данные не изменялись.

## 2026-11-18 — Действия над выбранными позициями

- Professional/staging: галочки выбирают позиции в текущей сессии; снизу появляется «Создать карточку». В Q выбирается «Создать новую» (существующий редактор склада) или «Использовать существующую» (сопоставление с существующей карточкой). Для нескольких позиций применяется последовательное подтверждение; связи сохраняет действующий Core `POST /inventory/counterparties/:id/catalog/:rowId/link`. Для уникального совпадения артикула существующий товар лишь предлагается, связь не создаётся автоматически.
- Нижнее действие «Удалить» пока **отключено**: существующий Core не предоставляет постоянного исключения позиций поставщика. Не заменять удаление временным скрытием в браузере или удалением складских карточек.
- Core нужен tenant-scoped идемпотентный API исключения и восстановления строк ассортимента. Исключения должны сохраняться после обновления/повторной загрузки документа, на других устройствах, при этом оригинал файла остаётся доступным. При обновлении сопоставлять только надёжные уникальные идентификаторы; не удалять неоднозначные совпадения и не затрагивать `InventoryItem`, `InventorySupplierOffer`, движения и историю.

## 2026-11-18 — Реализация API и UI в staging (обновление статуса)

- Ранние записи выше — историческая фиксация состояния до реализации. Теперь в **Core/staging** добавлены `excludedAt`, миграция и `POST /inventory/counterparties/:id/catalog/selection` с `{rowIds,excluded:true|false}`. `GET /inventory/counterparties/:id/catalog` возвращает активные позиции; `?excluded=true` — исключённые.
- **Professional/staging**: нижнее «Удалить» после выбора доступно с подтверждением; действие в Core скрывает строки без изменения `InventoryItem`, связей и исходного файла. В V-меню контрагента «Исключённые» позволяет восстановить позиции.
- При повторной загрузке исключение переносится на новую версию **только при однозначном совпадении SKU или штрихкода**. При дублирующихся/изменённых кодах автоматическое исключение не проводится, чтобы не скрыть другой товар.
- Индикатор после артикула: зелёный — подтверждённая связь Core; жёлтый — единственное совпадение SKU/штрихкода с карточкой без подтверждённой связи; серый — совпадения нет. Новые связи автоматически по совпадению кода не создаются.
- Создание/связывание нескольких отмеченных товаров производится последовательным вызовом существующих API с подтверждением каждого элемента. Единого атомарного пакетного создания карточек и подключения не добавляли — пользователь не теряет контроль над единицами учёта.
- Изменения **только в ветках staging**. Миграция должна быть применена на сервере перед эксплуатацией новых вызовов; прохождение CI/живое тестирование фиксируются отдельно.

## 2026-11-18 — Требование к динамическим столбцам классификации «Остатков» (Core, НЕ реализовано)

**Решение владельца:** отказаться от навязанной бесконечной иерархии `manufacturer → classificationPath → ...`. Для каждой компании/производителя в Остатках нужен **свой независимый набор именованных столбцов-критериев**. Примеры: CHI — «Категория», «Тип»; SEKTA — «Категория», «Тип», «Серия». Можно добавлять/переименовывать/упорядочивать/убирать столбцы и добавлять/переименовывать значения внутри каждого столбца. Одинаковый текст («Крем», «Краситель») разрешён в разных категориях и у разных компаний: значения привязаны к конкретному критерию, не образуют автоматически новую вложенную папку. Товар может иметь выбор по каждому установленному для компании критерию.

- Отображение должно упрощать поиск товаров: **не принуждать открывать каждый уровень `details` для прохождения всех столбцов**. Конкретная компоновка и сколько уровней показывать — на визуальную приёмку, но без многоэтажного раскрытия по каждому атрибуту.
- Не терять старые `category`, `productType`, `classificationGroupId`, `classificationPath`, идентификаторы товаров, складские балансы и движения. Миграция/совместимость должны сохранять значения и давать безопасный переход с существующей модели; нельзя автоматически переписывать товары на основе неясного соответствия.
- **Текущее Core ограничение:** `InventoryItem.classificationGroupId` указывает на один узел универсального `InventoryClassificationGroup` (parentGroupId). В `resolveItemGroup` при изменении legacy полей Core сам создаёт дерево `manufacturer / category / productType`. Нет отдельного API/сущности per-company критерия-столбца, значений и множественных назначений товару. Требуется именно серверная модель/API с контролем целостности и сохранением между устройствами — не localStorage и не дублирование в Professional.
- Требование к порядку производителей на Z1: пользователь должен уметь перетаскивать компании и фиксировать их порядок между сеансами/устройствами. Существующий `/inventory/items/reorder` сортирует **товары внутри одной компании**, не компании; отдельный server-side owner для порядка производителей отсутствует. Это тоже Core handoff, не использовать этот endpoint для имитации сортировки компаний.
- Состояние на текущий момент: в Professional/staging временно восстановлено отображение по существующим `category` и `productType` без серверного `classificationPath` (коммит `9603139`). Отдельная динамическая схема столбцов и перетаскивание компаний **ещё не реализованы**. Core/User/main не изменять в ходе этого шага.

## 2026-11-18 — Уточнение владельца: группы и значения (приоритет над прежним вариантом «столбцы по компаниям»)

**Приоритетное решение:** критерии классификации — это **общие для аккаунта Professional именованные группы**, а не отдельные наборы для каждой компании. Историческое описание выше «для каждой компании свой набор столбцов» **заменено этим уточнением**. Производитель — первый, системный признак, но не создаваемая вручную группа. Каждой пользовательской группе соответствует собственный список значений. Одинаковые слова допускаются в разных группах; выбранное значение одного товара не должно превращаться в иерархическую папку.

### Начальное состояние любого существующего и нового склада

| Стабильный ключ | Начальное отображаемое имя | Источник текущих данных | Управление |
| --- | --- | --- | --- |
| `manufacturer` | Производитель | `InventoryItem.manufacturer` | Системная, создаётся автоматически; имя критерия не изменяется |
| `category` | Критерий | `InventoryItem.category` | Создана системой по умолчанию; имя группы и список значений редактируются |
| `productType` | Тип | `InventoryItem.productType` | Создана системой по умолчанию; имя группы и список значений редактируются |
| `custom:<id>` | Имя, заданное пользователем | Новое безопасное хранилище значений | Создаётся, переименовывается, упорядочивается пользователем |

**Имена «Критерий» / «Тип» — начальные подписи**, не технические ключи. Переименование группы не изменяет значения и назначения товаров. Значения выбираются из справочника соответствующей группы, редактируются и добавляются внутри неё; одинаковое значение (например, «Крем») можно создать и использовать в разных группах. Товар может иметь выбранное значение **в каждой группе независимо**. В каждой группе допускается пустое значение. Количество пользовательских групп и значений не должно ограничиваться двумя старыми полями.

### Требуемая модель и совместимость Core (НЕ реализовано)

1. Tenant-scoped справочник **групп-критериев** с устойчивым ID/ключом, отображаемым именем, системным флагом, порядком. Отдельный tenant-scoped справочник **значений**, принадлежащих группе; значения имеют собственные ID и порядок. Отдельные назначения **товар ↔ группа ↔ значение**; не использовать `parentGroupId` в качестве способа хранения независимых критериев. Перед внедрением уточнить поддержку множественного выбора в одной группе; текущая спецификация — одно значение на товар в каждой группе.
2. При первом чтении существующего склада автоматически представить `manufacturer`, `category`, `productType` как три исходные группы, без изменения названий производителей и имеющихся значений. Существующие `InventoryItem.category` и `productType` обязаны остаться источником старых назначений до безопасного подтверждённого переноса. Не преобразовывать их в новые «группы» по путям `classificationPath` и не перезаписывать `classificationGroupId`.
3. Нужна атомарная, идемпотентная и проверяемая миграция значений старых двух полей в новые справочники/назначения. Сначала чтение и сравнение исходного и нового состояния **для каждого товара**, только потом переключение фронта на новые поля. Сохранить `itemId`, остатки, движения, цены, поставщиков и все другие инвентарные данные. Существующее дерево `InventoryClassificationGroup` не архивировать и не удалять автоматически; хранить отдельно до явного решения о дальнейшей судьбе.
4. До подтверждённого перехода гарантировать двустороннюю совместимость старых `category`/`productType` при создании/редактировании из Professional, а после — определённую стратегию синхронизации или прекращения legacy-пути. Нынешняя `resolveItemGroup` автоматически создаёт дерево из `manufacturer/category/productType`; нельзя использовать его для новой системы, оно должно быть изолировано от новых назначений.
5. Нужны безопасные API чтения и мутаций названий групп, значений, порядка групп, порядка значений и назначений на товарах; все серверные операции работают в текущем tenant. Изменения доступны на всех устройствах, не в `localStorage`. Редактор Professional должен показывать **первым Q список групп** («Производитель», «Критерий», «Тип», дополнительные); при выборе пользовательской группы — отдельный Q «Значения» с созданием/редактированием значений. Не возвращать «родительскую группу» и произвольные уровни дерева.
6. Навигация списка товаров: обычный вход по производителю, затем понятные категория/тип/товары; не требовать прохождения каждого добавленного критерия ради доступа к товару. Дополнительные критерии — данные карточки и выборочные способы организации списка, а не принудительная глубина вложенности. Порядок производителей перетаскиванием — отдельный Core handoff выше, существующий `/items/reorder` менять назначением нельзя.

**Статус:** только уточнение требований и handoff. Не менять Core/User/main, не объявлять модель готовой; не производить автоматическую миграцию или исправление записей склада силами Professional.
