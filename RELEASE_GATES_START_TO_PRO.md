# План закрытия релизов Professional: Start → Start+ → Pro

**Статус: техническая карта исполнения, не подтверждение готовности функций или утверждение состава тарифов.**
**Единая карта по уровням F/E/режим/UI/capability и защита после приёмки:** [`RELEASE_CLOSURE_MAP.md`](./RELEASE_CLOSURE_MAP.md) → реестр [`RELEASE_CLOSURE_REGISTRY.json`](./RELEASE_CLOSURE_REGISTRY.json). Эти документы — источник статуса закрытия, не дублировать статус в новых таблицах. Без новых CI.
**Область:** `co-va/professional` (UI), `co-va/core` (API/БД/права/деньги), `co-va/user` (потребительская сторона). Раздельные владельцы, без копий бизнес-логики.
**Ветки:** только `staging`; `main`/Amvera — только после отдельного разрешения владельца. Пока над Core работает другой исполнитель, не вносить параллельные изменения в Core.
**Источники договорённостей:** `co-va/core/COMMERCIAL_TARIFF_CONTRACT.md`, `BUSINESS_ARCHITECTURE.md`, `LOYALTY_FINANCE_CONTRACT.md`, `PROJECT_STATE.md`. При конфликте — уточнить, не подменять правила импровизацией.

## 0. Сначала построить защиту, потом закрывать функции

**Нулевой выпускной барьер:** общий сценарий исполняется **на реально запущенных `core/staging` + PostgreSQL + `professional/staging`**, а не только по мокающим тестам или опубликованному `core/main`. Каждая проверка привязана к точным SHA обоих репозиториев и версии API. В сценарии пользователя выявлен пример нарушения: UI запросил `POST /inventory/items/reorder`, которого не было на подключённом `core/main`; запись № сервер молча проигнорировал. Зелёный тест `core/staging` не доказывал работоспособность развернутого API.

1. **Карта владельцев данных:** Record/Time, Procedure/Service, Person, Sale, Settlement, FinanceOperation/Ledger, Stock, тарифы/readiness. Для каждой сущности — один серверный владелец, одна запись факта и один путь изменения. Старый и новый код сначала сопоставить; удалить дубли **только после доказанного переноса ссылок и проверки сохранности данных**, без «зачистки» репозитория целиком.
2. **Единый вход операции:** действия из Журнала и вне Журнала используют один доменный расчёт `Settlement` и собственные идентификаторы источников, а не две независимые реализации оплаты. Finance — единственный владелец денежного факта; Record отображает его проекцию.
3. **Защита без новых CI-workflow:** НЕ создавать новые GitHub Actions, не добавлять автоматический запуск полной проверки на каждое исправление. При работе выполнять только адресный тест изменённого контура и короткий синтаксический/контрактный контроль зависимостей. Полный сквозной прогон выполняет исполнитель **только при закрытии этапа/перед разрешённым релизом**, на согласованной связке Core + Professional + User и реальной тестовой БД. До завершения такого прогона этап не считается закрытым, даже если код запушен. Уже существующие CI других репозиториев не перестраивать ради этого плана.
4. **Данные без дублей:** идемпотентность по одному идентификатору операции, серверные транзакции, уникальные ключи/ограничения там, где это соответствует бизнес-модели, корректная обработка повторного нажатия, сбоя сети и двух устройств. История и платежи не стираются «очисткой UI».
5. **UI-гарантии:** канонический SHAD UI, существующие Z/Q/X, один контракт жестов и размеров. Запрет локальных «костылей» и полной перерисовки модала для исправления одной операции. Проверять закрытие/клавиатуру/скролл отдельно от бизнес-логики.
6. **Журнал релиза и регрессионных доказательств:** что закрыто, кто владеет, каким интеграционным тестом защищено, SHA прошедших сборок, какая версия реально работает в Amvera, оставшиеся блокеры. Не переносить `staging` в `main` по одному лишь успешному unit-тесту.

**Критерий закрытия функции:** реальная операция → факт в PostgreSQL → правильные экраны и API → повтор без дублей → коррекция/возврат → адресный исполняемый регрессионный сценарий → проверка согласованной версии на стенде. Успешная отрисовка и изолированные моки недостаточны. Абсолютно исключить будущие ошибки невозможно; сохранённые тесты и отдельный выпускной прогон должны обнаруживать типовые регрессии **до** выпуска.

**Режим без постоянных тормозов:**
- **Во время правки:** только сценарий изменённой функции и затронутых контрактов. Никаких полных сборок трёх проектов на каждое нажатие, косметическую правку или коммит.
- **При закрытии одной цепочки:** одно полное прохождение соответствующего бизнес-сценария на тестовом API и БД. Результат, версии и факты записываются в карту. Это не новое CI.
- **Перед выпуском Start / Start+ / Pro:** один целенаправленный общий регрессионный прогон всех уже закрытых цепочек. Без него не утверждать готовность к выпуску.
- **Защита от подмены теста:** согласованный сценарий и его ожидаемый результат считаются зафиксированным контрактом. Исполнитель не имеет права удалять, ослаблять, переписывать или отключать тест, чтобы получить PASS. Изменение такого контракта — отдельное согласование владельца с причиной и сравнением старого/нового результата. Git SHA закрытого этапа фиксируется; перед релизом проверяется diff тестов и исходных контрактов относительно этого SHA. Техническое принуждение к этому правилу на уровне прав GitHub требует отдельной настройки защиты, которой пока нет.
- **При сбое проверки:** исправлять сломанную функцию, не подгонять эталон и не обходить проверку. Полный CI не нужно перезапускать после каждой промежуточной попытки.

## 1. START — сначала минимальный законченный ежедневный бизнес-цикл

Порядок строго **по зависимостям**, не по простоте задачи. Исполнять малыми вертикальными срезами: один путь от UI до БД и обратно, затем зафиксировать тест.

| Этап | Закрываем одну законченную цепочку | Обязательное доказательство |
| --- | --- | --- |
| S1 | Профиль → одно рабочее пространство → прайс услуг и товаров → Контакты | Данные после перезапуска не теряются; отсутствуют вторые владельцы/дубли и неверные цены |
| S2 | **Журнал целиком:** День → Месяц → График → Список → единая карточка записи и Z/Q/X → создание, перенос, отмена, завершение, история | Каждый режим функционально и визуально завершён; везде канонические компоненты и одна модель Record/Time/Finance, без локальных дублей |
| S3 | Оплата **из записи**: цена/коррекция → выбор кошелька → полная/частичная оплата → долг → корректировка/возврат | Один Settlement и одна денежная операция на действие; суммы Record, Касса, ДДС и Z-отчёт сходятся; повторный запрос не удваивает платёж |
| S4 | **Продажа вне записи**: товар → количество → Контакт необязателен → цена/коррекция → оплата → возврат | Работает без искусственного Record и без записи во времени; тот же Settlement/Finance, что в S3; товарное движение связано с продажей, если предусмотрено учётом |
| S5 | Сквозной мобильный проход S1–S4 с реальным Core API/БД; повторный вход, повторная отправка, плохая сеть, пустые состояния | Скриншоты/логи и ручной выпускной прогон; Z/Q/X не прыгают; сообщение при неуспехе не исчезает; отсутствует ложное «сохранено» |
| S6 | Зафиксировать контракт Start, контрольные сценарии и SHA | При закрытии Start+/Pro обязателен повторный выпускной прогон **всех** сценариев Start; не на каждый PR |

### S2: как именно закрываем Журнал (визуально и функционально)

**Журнал — самостоятельный законченный этап, не «только оплата».** Работать небольшими последовательными частями, без большого редизайна, без новых локальных UI, без изменения всех режимов одним коммитом.

| Порядок | Поверхность | Условие приёмки |
| --- | --- | --- |
| J1 | **День** | Шкала времени и слоты из Time; создание записи/события/заметки; просмотр, редактирование, перенос, отмена; статусы и цвета; отсутствие задержек, двойных событий, прыжков Z |
| J2 | **Месяц** | Календарь, занятость, переключение месяца и рабочего пространства, переход в День; одно и то же состояние Record/Time |
| J3 | **График** (режим Месяца) | Рабочие/выходные дни, часы, массовые изменения и конфликты; штатные Shared Calendar и модальные компоненты, без обхода Time |
| J4 | **Список** | Режимы, правильные даты/суммы/статусы, переход к тому же Record Q; общий компонент строки и единый расчёт из Finance, без локальной альтернативы |
| J5 | **Карточка записи / подтверждение** | Один канонический `miniCard`, правильная геометрия, края и структура; одинаковые правила в Professional и User. Открытие из всех режимов ведёт к одному Record; без копий карточки и без CSS-костылей |
| J6 | **Весь Журнал** | Переходы между J1–J5 и перезапуск приложения, сценарии ошибок/повторов, соответствие серверу и сохранённому факту в БД; проверка на реальном мобильном интерфейсе |

**Реальные UI-владельцы в Professional:** `ui/ui.js` — общий экспорт; `ui/cards/mini-card.js` + `ui/cards/mini-card.css` — общий компонент мини-карты; `ui/record/runtime.js` — подтверждение Record с `miniCard`; `ui/record/record.css` — контекстное оформление подтверждения; `journal/день.js`, `journal/месяц.js`, `journal/график.js`, `journal/список.js` — режимы; `core/records/view.js` — просмотр Record. В User общий `ui/cards/mini-card.js` совпадает, но карточка записи получает другой контекстный CSS `record-summary-mini-card` в `ui/cards/mini-card.css`. Это **расхождение реализации, не доказательство, что один из вариантов уже визуально неверен**. Не исправлять все карточки одной заменой скругления. Сначала сопоставить видимое представление с эталоном и его назначением.

**Запреты:** не менять Z/Q/X и семейство SHAD UI ради локального экрана; не создавать вторую функцию Record Card; не добавлять второй список статусов, вторую палитру или обход Finance/Time; не переносить бизнес-логику в UI; не объявлять Журнал готовым по одному только успешному платежу.

**Проверки:** во время каждого J1–J5 — только адресные проверки; после J6 — один общий ручной интеграционный проход по реально связанным версиям. Никаких новых CI-workflow.

**Не утверждать автоматически**, что все перечисленные инструменты положены подписчику Start: это обязательный **сквозной контур запуска продукта**, а точный состав доступа определяется тарифным каталогом Core. Если базовая продажа/оплата назначается только в другом уровне, соответствующий сценарий остаётся общим фундаментом и проверяется в разрешённом тарифном режиме.

**Известные утверждённые ограничения Professional Start:** бесплатно, 1 рабочее пространство, до 10 товаров. Полный состав тарифных инструментов не зафиксирован данным документом — его нельзя выдумывать.

## 2. START+ — расширение без новой реализации Start

**Вход:** S1–S6 проверены на настоящей связке Professional/Core; эталон Start зафиксирован и повторно проверяется перед выпуском, без дополнительных CI.

| Этап | Что делается | Доказательство |
| --- | --- | --- |
| P1 | Core превращает опубликованный тариф Start+ в единый источник права, лимита и готовности. Наследование Start ⊆ Start+; сохранение существующих данных при смене подписки. | Server-side доступ разрешён/запрещён независимо от того, скрыта ли кнопка; права Start не ухудшаются |
| P2 | Закрываются **только инструменты и лимиты, реально включённые в Start+ через Администратора**. Для каждого — отдельный end-to-end сценарий, без копии бизнес-логики. | Инструмент показывает реальную готовность и работает при разрешённом праве; тест Start повторно зелёный |
| P3 | Платная подписка: счёт-снимок, оплата, начало/продление, сроки 30/216/540 дней, восстановление доступа/истечение, повторный платёж | Не начисляются дни дважды; история/данные сохраняются; срок не пересчитывается задним числом |
| P4 | Проверка действительных тарифных лимитов и границ безопасности в разных аккаунтах | Start: 1 пространство; Start+: 3; нельзя получить права другого tenant через UI/API |
| P5 | Релизный барьер Start+ | Перед выпуском вручную запустить сохранённые сценарии Start + Start+; не запускать полный набор после каждого PR |

**Неутверждённое:** лимит товаров Start+ и месячная цена. Не подставлять фиктивное значение. Текущая коммерческая реализация Core ещё не полностью переведена с покупки отдельных продуктов на исполняемые тарифные права.

## 3. PRO — функциональное расширение поверх двух закрытых уровней

**Вход:** сохранённые проверки Start и Start+ выполнены на реальной интеграции перед этим этапом.

| Этап | Что делается | Доказательство |
| --- | --- | --- |
| R1 | Включённые в Pro инструменты — только из канонического тарифа Администратора, с readiness `READY` / `TESTING` / `NOT_READY` | Права Pro включают Start+; «в тарифе» не равно «инструмент готов» |
| R2 | Сложные денежные источники, **если назначены Pro**: депозиты, личные счета, сертификаты, абонементы, скидки/программы, смешанная оплата | Никакого повторного денежного прихода при использовании аванса/депозита; остатки, погашения и возвраты согласованы |
| R3 | Складские и управленческие процессы **если включены**: движение, инвентаризация, заказ, отчёты и связи с продажей | Ни одной потери денежных фактов, остатков, аудита и межприложенных ссылок при коррекции |
| R4 | Нагрузочные и конфликтные случаи: параллельные записи/оплаты, повторные запросы, смена условий, обновление API и клиента в разное время | Идемпотентность, изоляция tenant, целостность и обратная совместимость |
| R5 | Релизный барьер Pro | Перед выпуском один полный прогон Start + Start+ + Pro; при нарушении старого контура не разрешать выпуск |

**Известное:** для Pro рабочие пространства и товары — без ограничения. Месячная цена Pro не утверждена. User имеет собственные три тарифа и собственную матрицу; её нельзя автоматически копировать из Professional.

## 4. Постоянный порядок исполнения

**Осмотр конкретного участка → назначение одного владельца → короткий адресный тест → минимальное изменение → проверка соответствующего сценария → фиксация закрытия.** Полный регрессионный прогон — только на выпускном рубеже. Никаких массовых «очисток дублей»: только адресная ликвидация второго источника, подтверждённая тем же тестом.

**Одна активная большая работа:** сначала S1–S6 и запуск Start-контуров. Start+ и Pro не разрабатываются параллельно, исключая необходимые общие модели/контракты, которые нужны уже Start.

**Правило работы других чатов:** ссылаться на эту карту и `PROJECT_STATE.md`; не добавлять CI и не переписывать регрессионные тесты ради зелёного результата; не называть этап закрытым без фактической интеграционной проверки; не менять архитектуру/UX/другой репозиторий без доказанной необходимости и разрешённых границ.

**Актуальный стартовый риск на 13.11.2026:** в `professional/staging` реализовано перетаскивание склада, но приложение отправляет API на `api.va-tools.ru`, где отсутствует `POST /inventory/items/reorder` из `core/staging`. Это пример того, почему развёрнутый контракт нужно проверять отдельно от зелёного CI. Пока другой исполнитель завершает Core, изменения в Core не вносить.
